# VectHare S11.4 + Similharity S10.3 — GUI connection setup

## Goal

Install the extension and server plugin into **disposable** SillyTavern, then configure the database **entirely in VectHare's GUI**. No `SIMILHARITY_SERVER_CONFIG_DIR`, `SIMILHARITY_LOCAL_QDRANT_URL`, hashed user directory, JSON editing, or shell exports are required for this release's GUI-supported connection setup.

The host's `enableServerPlugins: true` requirement and the backend server itself still apply. VectHare does not install/start Qdrant or Milvus.

## Install (Termux, Windows, Linux)

1. Back up your existing SillyTavern user data, extensions, plugins, and databases. Use a disposable profile and database first.
2. Stop SillyTavern; extract `VectHare-S11.4-GUI-Connection-Setup.zip` under `public/scripts/extensions/third-party/` so the folder's `manifest.json` is at `third-party/VectHare/manifest.json`.
3. Extract `VectHare-Similharity-S10.3-GUI-Connection-Setup.zip` under `plugins/` so `plugins/VectHare-Similharity/index.js` (or the plugin directory named `similharity` in your installation) is at the top level, not nested. Keep the plugin folder/name expected by your SillyTavern plugin loader; do not install duplicate Similharity copies.
4. Install plugin dependencies according to the plugin's package.json (`npm install` inside its directory), and ensure SillyTavern has server plugins enabled.
5. Start SillyTavern, open VectHare settings. The build status should detect **S10.3 / S11.4** (inspection only).

## Local Qdrant

1. Start your Qdrant server separately on the same Termux/Linux/Windows host as SillyTavern.
2. In VectHare: **Vector Backend > Qdrant**; keep **Use Qdrant Cloud** unchecked.
3. Defaults are `127.0.0.1` and port `6333`. This default requires **no setup file or environment variable**.
4. If you use a different loopback port, enter it in the GUI, then select **Save connection & test**.
5. The status shows the exact server-side endpoint and whether the connection/health checks succeeded.
6. On Termux, if SillyTavern and Qdrant run in different Android process/container/network namespaces, `127.0.0.1` refers to the SillyTavern process's network namespace. Forward or expose the Qdrant service appropriately; don't assume the browser device's localhost is the same machine.

## Qdrant Cloud / remote HTTPS

1. Select **Use Qdrant Cloud**.
2. Enter the Qdrant HTTPS URL and API key in the GUI.
3. Select **Save connection & test**. The token is sent once over the authenticated same-origin SillyTavern session to the plugin, stored in a restricted per-user server file, and omitted from all status/report responses.
4. The API key input is cleared after submission. Leaving it blank for a later edit retains the saved key only **when the endpoint is unchanged**; changing endpoints clears the previously saved key.
5. To revoke local stored configuration, select **Remove saved connection**. This does **not** revoke a cloud provider's API key at the provider.

## Milvus

1. Select **Milvus** under Vector Backend.
2. Enter `localhost:19530` or a remote server address. For remote servers, use a TLS connection; the GUI allows a full HTTPS URL and normalizes it to host:port.
3. Enter a token, or enter username/password to construct an authentication token in the Save request. Credentials are stored only in the server-side per-user connection file.
4. Choose **Save connection & test**. A successful connection does **not** authorize VectHare vector writes.

## Data and access handling

- Server config location is derived from SillyTavern's **authenticated user root**, under `.similharity-private/connections.json`, not from user-supplied path strings or extension settings.
- On POSIX/Termux/Linux, private directory/file mode checks enforce 0700/0600. On Windows the server relies on the user directory's Windows ACL inheritance; verify deployment ACLs before shared-machine use.
- The configuration routes require authenticated user context and a non-simple custom request header; the extension sends the SillyTavern request headers. They are configuration operations, not vector write permissions.
- Browser-side saved host/port labels are non-secret UI preferences. The actual backend endpoint is the server's saved configuration, and diagnostics query that authoritative state.
- Local mode can connect without saving; cloud mode and non-default local addresses require an explicit GUI save.

## What is intentionally NOT yet operational

S10.3 still explicitly refuses public v2 record reads/writes, and E02 blocks unverified vector insert/edit/delete/reindex/purge operations. Qdrant/Milvus legacy shared reads remain restricted. No live SillyTavern/backend certification has occurred. S11.4 solves configuration and initialization UX; it **does not reactivate** memory vectorization or guarantee full user workflows.

Full functionality requires authoritative chat/branch/source ownership, connecting the internal v2 read/write adapters to authenticated public routes, real-backend concurrency/durability acceptance, migration/inventory work and final host integration tests.

## If a connection still fails

- `S03_SERVER_CONFIG_MISSING` in cloud mode: save the Cloud configuration via the VectHare GUI (not environment variables).
- `GUI_CONFIG_DIRECTORY_UNTRUSTED` or `GUI_CONFIG_FILE_UNTRUSTED`: inspect host-side permissions/ACLs of the authenticated user's private directory; do not disable these checks.
- `S03_USER_DIRECTORY_UNVERIFIED`: SillyTavern host user/root directory contract is unavailable or malformed; record the host version and a redacted error trace.
- `S03_QDRANT_CONNECTION_FAILED`: Qdrant server unreachable at the actual server endpoint; check service and port from the host environment.
- `S03_QDRANT_AUTH_REJECTED`: remote API key or provider authorization failed.
- `VECTHARE_E02_OPERATION_DENIED`: an intentionally blocked vector *operation*, not a connection-setup failure.

No production-readiness claim is implied by the offline test results.
