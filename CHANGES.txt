VECTHARE+ CHANGES — Persistent/Resumable Vectorization
=======================================================
Date: 2026-08-31
Base: Dogoo9 bug-fix fork of VectHare

This file lists every change made for the "continue vectorization from where
it left off" feature set. Review each item below against the diffs.

----------------------------------------------------------------------------
1. NEW FILE: core/vectorization-control.js
----------------------------------------------------------------------------
- Tiny run-control module: pauseVectorization(), resumeVectorization(),
  stopVectorization(), resetControlState(), isVectorizationPaused(),
  isVectorizationStopped().
- In-memory state only, BY DESIGN. There is no "checkpoint file" to corrupt:
  the vector database itself is the source of truth for progress. Every
  successfully embedded vector is already written through immediately (existing
  per-batch write behavior), so resume = "re-run sync, it skips what exists".
- resetControlState() is called at run start/end/abort so stale pause/stop
  flags can never wedge the extension across runs.

----------------------------------------------------------------------------
2. core/chat-vectorization.js
----------------------------------------------------------------------------
a) Added import of the run-control module (vectorization-control.js).

b) synchronizeChat() — pause gate at top:
   While paused, automatic sync stays idle and returns immediately. The
   pending queue is re-derived from the DB on the next run, so nothing is lost.

c) synchronizeChat() — batch loop honors Pause/Stop:
   The inner while loop checks the stop/pause flags each iteration and breaks
   out, leaving the remainder of the queue untouched. All already-completed
   items are persisted, so any later run continues from the break point.

d) synchronizeChat() — NEW reverse sync pass (Step 1.5), inserted before
   queue construction:
   - Deletes "ghost vectors": stored hashes that no longer match any current
     chat content (edited messages produce new hashes; deleted messages
     produce orphans). This makes the collection a true mirror of the chat.
   - Keep-set is built from groupedItems (combined hashes), NOT raw per-message
     hashes — required for conversation_turns / message_batch strategies,
     otherwise every grouped chunk would be wrongly classified as a ghost.
   - Protected from deletion: scene composite chunks (metadata.isScene),
     summary chunks (isSummary*/parentHash), and chunks disabled-by-scene.
   - Only runs when per-chunk metadata is resolvable from the backend
     (getSavedHashes with includeMetadata=true); skips safely otherwise.
   - Wrapped in try/catch: reverse-sync failure never blocks forward
     vectorization; orphaned per-chunk settings metadata is cleaned up.

e) vectorizeAll() — Pause/Resume/Stop controls:
   - Wires Pause/Resume/Stop buttons into the progress panel via
     progressTracker.setControls().
   - Pause: loop waits (polls every 300ms, no busy burn) until resumed; the
     panel switches to "Paused" state showing Resume/Stop.
   - Stop: run ends cleanly with a completion message ("work kept, continue
     anytime via Vectorize Chat"). Completed vectors are all saved.
   - resetControlState() on: send-press abort, chat-changed abort, normal
     completion, and the outer catch on failure.

f) NEW export: checkUnfinishedVectorization(settings)
   - Read-only diff of grouped chat items vs stored collection hashes.
   - Returns { hasBacklog, pending, total } for resume-on-load detection.
   - Never vectorizes anything; fails soft (returns null) on any error.

----------------------------------------------------------------------------
3. ui/progress-tracker.js
----------------------------------------------------------------------------
a) BUG FIX: removed a stray literal "9" inside generateStatusMessage() that
   was a JavaScript SyntaxError — this broken syntax would have prevented the
   entire module (and everything importing progressTracker) from loading at
   all. The file now parses.

b) New Pause / Resume / Stop buttons on the progress panel (menu_button
   styling, FontAwesome icons, hidden unless wired via setControls()).

c) New methods:
   - setControls({onPause, onResume, onStop}) — wires callbacks and shows
     Pause/Stop buttons at run start.
   - hideControls() — hides buttons on completion/failure.
   - markPaused(message) — freezes timers, swaps Pause button for Resume.

d) complete() now calls hideControls() and guards against stats.startTime
   being null (defensive: avoids NaN duration if completion races start).

NOTE: this file was rewritten in full (identical logic otherwise), so diff
it as a whole rather than line-by-line.

----------------------------------------------------------------------------
4. index.js
----------------------------------------------------------------------------
a) Added import of checkUnfinishedVectorization.

b) NEW: offerResumeOfUnfinishedVectorization()
   - On startup and on every CHAT_CHANGED, checks the loaded chat for backlog.
   - If pending > 0: shows a 20s toastr notification with the pending/total
     count; clicking it runs vectorizeAll() (which continues exactly where
     the previous run left off, per the checkpoint-free design above).
   - Failures are logged and swallowed — resume detection can never block
     extension startup.

c) Hooked into event_types.CHAT_CHANGED handler + a one-time setTimeout
   (5s after init) for startup (page reload / SillyTavern reopen).

----------------------------------------------------------------------------
WHAT THIS GIVES YOU (user-visible behavior)
----------------------------------------------------------------------------
- Vectorize Chat: progress panel now has Pause / Resume / Stop.
- Pause: in-flight request finishes and saves, no new work starts; Resume
  continues. Survives closing the panel while paused.
- Stop: ends the run keeping all completed work.
- Crash / page reload / browser closed mid-run: next time VectHare init or
  the chat loads, a notification offers to continue — it picks up from the
  first not-yet-vectorized item, determined from the DB (not a cursor).
- Edited/deleted old messages: their stale vectors are removed on the next
  sync pass (ghost cleanup), so retrieval can't surface content you deleted.
- Pause/Stop states are intentionally NOT persisted: on reload, "resume"
  simply means re-running sync, which is the same continuation. No state
  file to corrupt, no migration, no versioning problems.

----------------------------------------------------------------------------
RISKS / REVIEW NOTES
----------------------------------------------------------------------------
- Reverse sync deletes vectors whose hashes are absent from the current chat.
  It is metadata-gated and protects scene/summary chunks, but if you have
  chunks in the chat collection that come from OTHER sources (manual inserts,
  custom tooling), review (2d) before trusting deletion. The protected-class
  check also consults per-chunk settings metadata (disabledByScene etc.).
- The resume toastr fires on every CHAT_CHANGED while backlog exists (e.g.,
  while auto-sync is disabled or you keep declining). It is dismissible;
  consider a "don't ask again for this chat" setting if it's noisy.
- checkUnfinishedVectorization ignores min_chat_length; resume offers appear
  even for short chats (matching synchronizeChat's own behavior).
- Pause during a long embedding batch: a batched server-side insert
  (insertVectorItems batches of up to 50) finishes the current batch before
  the flag is observed — expected "drain in-flight" semantics.
- No changes made to: backends/*, chunking.js, content-vectorization.js,
  core-vector-api.js, collection-metadata.js (only consumed), or any UI
  styling files (buttons reuse existing .menu_button styles).

ROUND 2 FIXES (after live testing — 2026-08-31)
============================================================================

Test findings: (1) "Sync Chat" button did nothing. (2) No way to resume
after reload despite chunks persisting. (3) A 0-chunk "ghost" chat appeared.

R1. core/chat-vectorization.js — vectorizeAll() — "Sync Chat" dead button FIXED
    Root cause: legacy global gate `if (!settings.enabled_chats) return;`.
    `enabled_chats` defaults false and NO UI code sets it anymore (per-
    collection autoSync replaced it) — so the button no-op'd for everyone,
    silently. Replaced with a per-collection autoSync check that shows a
    warning toast explaining how to enable sync, instead of failing silently.

R2. core/chat-vectorization.js — checkUnfinishedVectorization() — ghost FIX +
    robustness:
    - Now only inspects collections present in the registry (registerCollection
      only fires after a successful insert). Previously it read the vector DB
      for the chat's collection even when none existed; some backends CREATE an
      empty collection on read, which discovery then reported as a 0-chunk
      ghost chat. Prevented at the source.
    - Returns null when the collection isn't in the registry yet so callers
      can distinguish "not discovered yet (retry)" from "definitively none".
    - Removed the autoSync gate: resume detection works regardless of whether
      auto-sync is currently enabled.

R3. index.js — resume detection made startup-race-proof:
    - offerResumeOfUnfinishedVectorization() now polls up to 5 attempts
      (3s apart) while collection discovery is still populating the registry,
      instead of one fire-and-forget attempt at 5s (which lost the race and
      never showed anything).
    - Deduplicated the toast into showResumeToast(); clicks on it run
      vectorizeAll() = "continue from exactly what's missing".

R4. ui/ui-manager.js — persistent "Continue Vectorization" button:
    - New action button in the Actions card, hidden by default, shown only
      while backlog exists (driven by updateContinueVectorizationButton()).
      Clicking runs vectorizeAll(); SD Booth persists as long as work remains.
    - New exported updateContinueVectorizationButton(hasBacklog, pending, total).

R5. ui/ui-manager.js — auto-sync modal now has a "Continue" action:
    The prompt shown when enabling auto-sync on a chat with an existing
    collection offered only Connect / Re-vectorize. Added "Continue":
    enables auto-sync for the chat then immediately runs vectorization,
    which resumes from the first not-yet-vectorized group (keeps all
    completed vectors; nothing is re-embedded).

R6. Verification pass: full re-read of chat-vectorization.js control flow,
    imports (getCollectionRegistry/parseRegistryKey/deleteVectorItems all in
    scope for the reverse-sync and resume-check additions), pause/stop paths,
    and the registry-gated resume check. No broken references found.

Known behavior after these fixes:
- Flow: enable Auto-Sync → modal → click "Continue" → vectorization runs and
  resumes from wherever it stopped (e.g. 5/1206). Reload mid-run → on chat
  load, either the toast or the (now visible) "Continue Vectorization" action
  button picks it up. "Sync Chat" from the Actions card does the same thing.
- Existing ghost chat: delete it via the trash icon in the auto-sync modal
  (it's stale from the pre-fix behavior; nothing will recreate it now).
- Resume polling on a chat that never had vectorization: quietly gives up
  after ~15s; zero backend reads (registry-gated), no cost.

ROUND 3 FIXES (weird-behavior sweep — 2026-08-31)
============================================================================
Scenarios verified per user request: vectorizing a chat with nothing in it,
choosing options WHILE vectorizing, SillyTavern restart behavior, popups.

S1. "Vectorizing an empty chat" — FIXED (two bugs):
    - vectorizeAll() on a chat with 0 non-system messages previously ran a
      full sync cycle and toasted nonsense success ("Vectorized 0 messages")
      with a 0/0 progress panel. Now short-circuits honestly: "This chat has
      no messages to vectorize."
    - CRITICAL: synchronizeChat() read the vector DB BEFORE checking whether
      the chat had any content. Combined with backends that create-on-read,
      enabling auto-sync on a fresh empty chat could manifest a 0-chunk ghost
      collection on disk. (With round-3's empty-chat guard in vectorizeAll the
      manual path can't reach it; note the create-on-read behavior is a
      backend characteristic, not something VectHare code does on purpose.)

S2. "Choosing options while vectorizing" — re-entrancy FIXED:
    - vectorizeAll() had no guard: double-clicking Sync Chat, or clicking
      Continue while a run was live, spawned a SECOND concurrent run that
      interleaved database writes, fought over the singleton progress panel,
      and re-wired Pause/Stop callbacks under the first run (weird UI states).
      Now: a module-level run flag rejects re-entry with an informative toast
      ("use Pause/Stop on the panel instead"). Flag is cleared on every exit
      path: completion, stop, abort, failure, blocked-bailout, empty chat.

S3. Mid-run message generation — no longer aborts the run:
    - Old: any generation starting mid-run made synchronizeChat return -1 and
      vectorizeAll showed "❌ Blocked or disabled" — a scary failure for a
      completely normal event. Now: the run WAITS (up to 30 consecutive
      seconds) for the transient block to clear and keeps going; only a
      sustained 30s+ block bails out gracefully, telling you everything
      completed is saved. Same grace applies to the sync mutex and pause.

S4. "Restart ST behavior" — traced, no change needed to storage semantics:
    - All run state is in-memory only (intentional). On restart the vector DB
      is the checkpoint: resume-on-load detects backlog via registry-gated
      hash diff and offers Continuation (toast + persistent button). What you
      saw persisted after your reload (5/1206) is exactly correct behavior.
    - Auto-sync events fire on chat change even after restart; with resume
      now bypassing the autoSync gate, the Continue button/toast appear
      regardless.

S5. Notification cleanup:
    - Resume toast/button no longer appear while a run is already active
      (isVectorizationActive() guard) — no more nag-while-working.
    - "Blocked or disabled" failure toast eliminated (see S3).
    - Empty-chat fake success toast eliminated (see S1).
    - Stop success toast wording unchanged (accurate).

Also fixed during this round: a botched intermediate edit that briefly
replaced the -1 handling block with placeholder text was caught and fully
restored in the same pass (final file verified coherent).

— Round 3 end. For behavior contract summary, see S1-S5 above.

ROUND 4 FIXES (final bug sweep — 2026-08-31)
============================================================================

T1. Resume affordance after Stop — FIXED (deadlock):
    After stopping mid-run and STAYING in the same chat, the Continue button
    never appeared: the backlog check only ran on CHAT_CHANGED, so the user
    had no way to resume without reloading the page. Now onVectorizeAllClick
    re-runs the resume check when a run ends, so button/toast always reflect
    the current chat's true backlog state (including "hidden" when complete).

T2. Duplicate startup toasts — prevented:
    CHAT_CHANGED fires on startup in addition to the one-time timer, so the
    resume check could run twice and stack two identical toasts. RESUME_CHECK
    toast now uses preventDuplicates: true (button update is idempotent).

T3. Sync Chat with per_scene strategy — fake success FIXED:
    per_scene vectorizes via scene markers, not chat sync. Previously ran a
    pointless cycle and toasted "Vectorized 0 messages" success. Now: honest
    info toast explaining scenes are vectorized from scene markers.

T4. Cross-collection metadata loss — prevented (data safety):
    Reverse sync previously deleted per-chunk settings metadata for ghost
    hashes. But chunk metadata is stored GLOBALLY by hash across ALL
    collections - a hash removed from this chat's collection may still be a
    live chunk in another collection, and deleting its metadata would destroy
    that collection's user settings (conditions, links, disable state).
    Orphaned metadata for genuinely dead hashes is harmless; deletion removed.

Verified clean this round (re-traced, no changes needed):
- vectorization-control.js flags reset on all exit paths
- progress panel Pause→Resume swap logic (buttons, timer restart)
- re-entrancy guard placement (after sync-call, before throws/returns)
- resume poller: isVectorizationActive guard, registry-gated reads,
  preventDuplicates, idempotent button state
- empty-chat + per_scene guards clear run flag
- chat-vectorization.js imports all still used / in scope after T4 change

ROUND 6 FIXES (sixth sweep — 2026-08-31)
============================================================================

V1. Permanent-fail infinite loop — FIXED (pre-existing, pre-VectHare+):
    Items that fail to embed are not written to the DB; on the next loop
    iteration they return to the queue and retry indefinitely. If even one
    source item ALWAYS fails (e.g., content the provider reliably rejects),
    "remaining" never reaches 0 and vectorizeAll loops forever, hammering
    the provider. This existed before VectHare+ but became acute with the
    re-entrancy guard (only one run can exist; a stuck run wedges it).
    Fix: consecutive all-fail detection in the run loop - 10 consecutive
    iterations with attempts but ZERO successful chunk inserts aborts the
    run honestly ("completed vectors saved; failed items retry next sync").
    Normal transient outages (one bad batch, then recovery) reset the counter
    and never trigger this.

V2. Reverse-sync per-message performance tax — FIXED (regression from R1):
    The ghost-cleanup pass fetches FULL collection metadata (up to 10k chunk
    entries) on every synchronizeChat call - which includes every message
    event during normal chatting and every vectorizeAll iteration. On large
    collections this caused a heavy per-message payload. Now throttled to
    once per 5 minutes across all passes via module-scope timestamp.
    Behavior unchanged otherwise; cleanup still runs promptly at most 5 min
    after any edit/delete.

V3. Stop honored during generation-stall wait — FIXED:
    The R3 "wait out message generation" loop skipped pause/stop checks;
    a hung generation made the Stop button dead for exactly that window.
    Wait loop now exits on Stop or Pause flags (normal stop-check logic
    resumes right after and handles them).

Known cosmetic quirk (NOT fixed, documented): processedCount in the run
summary counts ATTEMPTS - retried/failed items inflate the message count
slightly during failure-heavy runs. Display-only; the authoritative state
remains the DB.

— Round 6 end. 6 rounds total.

ROUND 7 (user test feedback — 2026-08-31)
============================================================================
Seven items from live testing. All addressed.

W1. Resume toast no longer runs vectorization on click:
    Popup is pure information now: "Use the Continue Vectorization button
    in the Actions panel". The button remains the single persistent
    affordance. (User preference - click-to-run was surprising.)

W2. Config fingerprint enforcement (THE IMPORTANT ONE):
    Every run now computes a fingerprint of
    {embedding provider, model, chunking strategy, batch size, chunk size},
    hashed and persisted on the collection metadata
    (vectorizationConfigFingerprint). At run start:
    - No stored fingerprint (first run) -> store and proceed.
    - Same fingerprint -> proceed.
    - MISMATCH + collection has vectors -> run BLOCKED with a persistent
      error toast explaining: restore previous settings, or re-vectorize
      via the Content Vectorizer (purges + rebuilds with new settings).
    - Mismatch + collection empty -> proceeds and adopts new fingerprint.
    This guarantees "continue" can never mix vectors from incompatible
    settings. Fingerprint failures degrade gracefully (warn + continue).

W3. Duplicate-vector self-healing:
    Every reverse-sync pass now counts hash occurrences in the collection;
    any hash stored MORE THAN ONCE has all copies deleted, then forward
    sync re-inserts exactly one clean copy in the same pass. Runs are also
    throttled (R6) so healing happens promptly but cheaply. The duplicate
    you saw was most likely written across an extension-update boundary
    (code swapped mid-run); ongoing runs can't produce them, and any that
    exist are healed within 5 minutes of the next sync.

W4. Chunk counter fixed (was showing 1/1):
    Root cause: the per-item embedding callback fires with (1,1) - one item
    per insert - and clobbered the panel's chunk counter every item.
    vectorizeAll now drives the counter from whole-collection truth:
    done = totalGroups - remaining (self-corrects as chat grows during
    catch-up). Counter line now shows real totals, e.g. 300/1206.

W5. Stop button feedback:
    Stop must drain the in-flight embedding request before the run ends
    (unavoidable short delay), but it was silent. Now: immediate panel
    status "Stopping - waiting for the in-flight embedding..." + an info
    toast, followed by the normal completion message when the drain ends.

W6. Auto-sync modal "Continue" made prominent:
    The button existed since R2 (leftmost footer button) but was visually
    identical to Connect/Re-vectorize and evidently too easy to miss.
    Now: highlighted border, label "Continue (Resume)", and a tooltip that
    explicitly says it does NOT re-vectorize and keeps completed vectors.
    If you still see only Connect/Re-vectorize, hard-refresh (Ctrl+Shift+R)
    - stale cached UI is the likely culprit.

W7. ETA on the progress panel:
    Time stat now shows elapsed + ETA, e.g. "1m 12.4s · ETA 25m 3s".
    Computed from average completion rate (stable over a 1200-item run,
    unlike last-batch jitter). Implemented via a stashed value appended by
    the 100ms timer - an earlier draft let the timer clobber the ETA text.

Also caught during this round (self-review before shipping):
- A duplicate `lastReverseSyncAt` declaration briefly introduced (would have
  been a module-killing SyntaxError) - caught and removed immediately.
- ETA text clobbering by the elapsed timer - redesigned into the timer path.

ROUND 9 (settings-continuity audit — 2026-08-31)
============================================================================

Y1. Fingerprint did NOT guard auto-sync — CRITICAL GAP, FIXED:
    The user's "important" requirement was: continuing must use the same
    vectorization settings. vectorizeAll enforced this for MANUAL runs, but
    event-driven auto-sync (new messages vectorizing in the background)
    bypassed the fingerprint entirely. Changed embedding settings + auto-sync
    enabled = new messages silently embedded with incompatible vectors into
    the existing collection. Silent poisoning, exactly what the check exists
    to prevent.
    Fix: synchronizeChat now runs the same fingerprint check when serving
    auto-sync (not manual bypass). On mismatch: refuses to add vectors,
    shows ONE persistent error toast (fail-closed), logs the reason. Manual
    runs still bypass this gate - vectorizeAll has its own stricter blocking
    check. Also: auto-sync now RECORDS the fingerprint if absent, so a
    collection fed purely by auto-sync still gets continuity verification
    on later manual runs.

Y2. Fingerprint computation unified:
    R7 computed the fingerprint inline in vectorizeAll. R9 extracts
    computeVectorizationConfigFingerprint(settings) as the single source of
    truth, used by both vectorizeAll and synchronizeChat. The two check paths
    can now never drift (e.g., one hashing a field the other forgot).
    Also added a missing null-guard: fingerprint computation failure now
    fails-open with a warning instead of undefined-comparison behavior.

Y3. ETA inflation across Pause — FIXED:
    ETA averaged from run start; paused minutes counted against it, so
    resuming after a long break showed a garbage (too-low) ETA.
    Fix: onPause records the pause timestamp; onResume shifts
    stats.startTime (and lastBatchStartTime) forward by the pause duration.
    Elapsed and ETA now measure working time only.

Y4. Post-Stop nag — FIXED:
    Deliberately stopping a run was immediately followed by the resume check
    toasting "unfinished vectorization!" - rude and redundant.
    Fix: vectorizeAll sets lastRunStoppedByUser on user Stop; index.js
    consumes it (consume-on-read) to skip the toast for THAT check only.
    Button still updates. Later chat changes still toast normally.

Self-caught during this round (fixed before shipping):
- First draft of the shared fingerprint helper used a sync globalThis cache
  for the model-field lookup that did not exist (model would silently drop
  out of the fingerprint). Replaced with a proper async import-based helper.

Verified clean this round:
- Auto-sync gate placement: after autoSync-enabled check, before any DB read;
  bypassAutoSync paths skip it entirely (manual runs check in vectorizeAll)
- One persistent toast max (autoSyncFingerprintWarned latch) - no toast spam
  per message event; latch resets on... (note: latch is session-wide, so if
  the user FIXES the mismatch in-session, no further reminder appears until
  reload. Acceptable: the blocked state is also visible as missing vectors.)
- Resume-clock shift affects both ETA and average-speed fallback paths
- consume-on-read flag: fresh run start clears it; single consumer in index.js
