# S10.1 — Authenticated SillyTavern user directory portability fix

**Scope:** Similharity S10 plugin only. No backend capability promotion.

## Observed failure

`POST /backend/init/qdrant` returned `HTTP 403; S03_USER_DIRECTORY_UNVERIFIED` before Qdrant was contacted. S03 assumed `req.user.directories.vectors` was already an absolute, existing path. SillyTavern can construct its paths with a relative `DATA_ROOT` via `path.join(DATA_ROOT,handle,...)`.

## Corrective changes

- Resolve SillyTavern-provided relative OR absolute paths with native Node `path.resolve`.
- When the authenticated host supplies `directories.root`, require the resolved `vectors` directory to be exactly its immediate `vectors` child.
- Verify the root exists and is a directory. Create only the missing empty `vectors` folder under that verified root (not a database, collection or vector file).
- Refuse symbolic-link substitution for the final vectors directory and refuse canonical paths escaping the verified root.
- Preserve per-process cross-user physical directory collision rejection.
- Preserve rejection of relative paths when the authenticated host does not provide a root; paths provided by browser request bodies and query strings are still never used.
- No modifications to Qdrant or Milvus credentials, write routes, v2 execution, migration, or production capability status.

## Compatibility

Plugin release version `3.2.10-s10.1`; extension `2.2.0-alpha.s11.2` must be installed as a matched pair because S11 pins an exact source fingerprint. The plugin requires `SIMILHARITY_SERVER_CONFIG_DIR` and a private per-user configuration file as before.

**Limits:** Verified using offline Node/Linux tests. No Termux/Windows/native-SillyTavern acceptance has been performed. Windows ACL and private configuration policy require real-host testing before a security certification claim.
