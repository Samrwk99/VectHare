# S11.1 Qdrant initialization compatibility correction

## Cause confirmed from source
VectHare S11 `backends/qdrant.js` submitted `host`, `port`, `url`, and/or `apiKey` keys to `POST /api/plugins/similharity/backend/init/qdrant`. Similharity S10 `validateClientConfig()` permits only `{}` or `{ "configId": "default" }` and returns `403 S03_CLIENT_CONFIG_FORBIDDEN` on other client-supplied connection fields.

The standalone Qdrant diagnostics path also sent browser connection fields and could report client-local configuration as mandatory even though S10 ignores it.

## Changes
- Qdrant backend initialization now posts only `{ "configId": "default" }`.
- Qdrant diagnostics posts the same selector, uses response `code` (allowlisted characters) rather than including arbitrary backend response bodies, and no longer insists on browser-configured cloud API keys/local host/port.
- The UI notes that S10 uses server-managed connection settings; the old connection fields are not authoritative.
- A historical C05 test assertion was updated to reflect server-side secret resolution, and a new S11.1 regression test added.
- No Similharity code or runtime capability policy was modified. Mutations stay disabled.

## Live setup still required
See `S03-SERVER-CONFIG-RUNBOOK.md` in the Similharity S10 ZIP. For a local Qdrant instance, the protected configuration value is `{ "url": "http://127.0.0.1:6333" }`, **not** a VectHare UI field. Cloud connections need a root HTTPS URL and `apiKey` in that private configuration file. `SIMILHARITY_SERVER_CONFIG_DIR` must be an absolute private directory and must be present in the SillyTavern server process's environment when it starts. Its per-user subfolder is SHA256 of the *authenticated* profile handle (or fallback user ID), never a manually chosen browser value. File permissions must pass the S03 checks. Do not send credentials through browser initialization or logs.

## Verification

- `node --check` passed for edited executable files.
- No live Qdrant or SillyTavern acceptance performed.
- An HTTP 409 with `S03_SERVER_CONFIG_MISSING` after this patch indicates expected missing server provisioning; HTTP 403 with `S03_AUTH_UNVERIFIED` or related identity code indicates the authenticated host context still needs inspection.
